# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A resume site for Alison Rafael Marinho Gonçalves, sourced from his LinkedIn export, plus a v2 backend (auth + Blog) now under active development. Content, audience, and stack decisions were made deliberately — see [`CONTEXT.md`](./CONTEXT.md) for domain vocabulary (including the v1/v2 split) and [`docs/adr/`](./docs/adr/) for architectural decisions before changing scope or infrastructure.

Note: `/home/argmalison/projects/alisonrafael.me` (an earlier Angular/NestJS/Mongo attempt at the same site) exists on disk but is abandoned in favor of this project.

## Repo layout

npm workspaces monorepo — see [ADR 0002](./docs/adr/0002-npm-workspaces-monorepo.md) for why. Three workspaces — `web-client`, `server`, and `shared` (data both apps need, e.g. the Tech Stack list; see [ADR 0008](./docs/adr/0008-shared-workspace-for-cross-app-data.md)) — orchestrated from the root `package.json`. `shared` must be built (`npm run build:shared`) before either consumer, since both import its compiled `dist/`, not raw source.

## Commands

Run from the repo root:

- `npm run dev:web` — Next.js dev server (Turbopack) for `web-client`, pinned to port 5173 (not Next's 3000 default — that collides with `dev:api`'s NestJS port; see [ADR 0013](./docs/adr/0013-migrate-web-client-to-nextjs-app-router.md))
- `npm run dev:api` — NestJS dev server (watch mode) for `server`
- `npm run build:web` / `npm run build:api` — build one workspace
- `npm run build` — build both

Per-workspace commands (`npm run lint`, NestJS's `npm run test`/`test:e2e`, etc.) still work via `--workspace=web-client` / `--workspace=server`, or `cd` into the workspace directly. `web-client`'s `npm run start` runs the same `output: 'standalone'` build Docker ships — `next start` doesn't work with that config (Next.js warns and exits abnormally), so this script copies `.next/static`/`public/` into the standalone tree by hand before running `node .next/standalone/web-client/server.js`, exactly like `web-client/Dockerfile`'s run stage.

## Stack

- **`web-client`**: Next.js 16 (App Router, `output: 'standalone'`) + React 19 + TypeScript + Tailwind CSS v4 (CSS-first config via `@theme` in `src/app/globals.css`, no `tailwind.config.js`) + Framer Motion (Admin Panel only — the public site has no scroll/entrance animation). Migrated wholesale from Vite + React Router — see [ADR 0013](./docs/adr/0013-migrate-web-client-to-nextjs-app-router.md) for why (real per-route SSR, replacing an abandoned meta-tag-injection approach — ADRs 0011/0012). The public site's look is modeled on lucasmontano.com: strictly black-and-white, system font stacks (Helvetica sans / serif / mono — no webfonts), square corners, full-bleed 1px rules — see the `globals.css` bullet below.
- **`server`**: NestJS + TypeORM + MariaDB (`mysql2` driver) + JWT auth (`@nestjs/jwt`, `@nestjs/passport`, `passport-jwt`) + `class-validator`/`class-transformer` + `@anthropic-ai/sdk` (trend discovery/draft generation, see [ADR 0007](./docs/adr/0007-anthropic-api-for-trend-discovery.md)). See [ADR 0003](./docs/adr/0003-mariadb-typeorm-backend-datastore.md) for the datastore choice. `server/tsconfig.json` uses `"module": "nodenext"` — every relative import needs an explicit `.js` extension, including in files that don't exist yet.

## Architecture

### `shared/`

- `src/index.ts` — currently just `techStackGroups` (the Tech Stack, see `CONTEXT.md`), canonically owned here. `web-client`'s `en.ts` imports it to render the public Skills section; `server`'s trend-filter agent imports the same array to build its prompt. See [ADR 0008](./docs/adr/0008-shared-workspace-for-cross-app-data.md) for why this exists and what it cost (`web-client`'s Docker build lost its self-contained-context independence — see Deployment below).

### `web-client/`

Next.js App Router (see [ADR 0013](./docs/adr/0013-migrate-web-client-to-nextjs-app-router.md)): routing lives in `src/app/`, but most actual component/page logic still lives in `src/{components,content,i18n,blog,admin,lib}` exactly as it did under the old Vite SPA — `src/app/**/page.tsx` files are mostly thin composition or re-exports over that code, not where the logic itself is written. Server Components by default; a file needs `'use client'` only where it touches browser APIs, hooks like `useState`/`useEffect`, or a browser-only library. Next.js still renders a Client Component tree once server-side for its initial HTML even with `'use client'` present — code in that first-render path (e.g. a `useState` initializer) that unconditionally touches `window`/`localStorage` will crash the build; guard it with `typeof window === 'undefined'`.

- `src/app/layout.tsx` — the root layout: site-wide fallback `<head>` metadata (title/description/OG/Twitter tags, favicon/manifest), applies to every route that doesn't set its own `generateMetadata`.
- `src/app/globals.css` — the `@theme` tokens (`--font-sans/serif/mono` system stacks; `--color-ink`, `-ink-dim`, `-surface`, `-surface-raised`, `-rule` (full-strength divider), `-line` (quiet hairline)), the `--gutter` page-gutter variable, and the `mono-label` utility (tiny uppercase mono text used for indexes/eyebrows/kickers). `--color-accent*` are deliberately just aliases of ink: the public site uses no accent color, but the Admin Panel shares these tokens and still styles buttons/links with them — so don't delete them or Admin loses its buttons. The Admin Panel is otherwise unstyled by the public redesign and simply inherits the monochrome palette.
- `src/app/page.tsx` — the resume (`/`), an async Server Component (`await getResumeContent()` — see `src/i18n/index.ts`, since the Resume Profile part of the content is now a live, cached API fetch, not a static import). Full-bleed, numbered sections, each closed by a 1px rule: `Hero`, then `01 / About` (the career numbers), `02 / Experience`, `03 / Skills`, `04 / Credentials`, `05 / Contact`, all via the shared `Section` (index label in a narrow left rail + large serif headline + body). No client JS in the page's own markup — only `LiveCursorOverlay` is a client island.
- `src/content/en.ts` — the static UI copy only (hero greeting, section titles, footer), typed by `src/content/types.ts`'s `StaticResumeContent`. The Resume Profile facts (name/headline/location, top skills, tech stack, languages, certifications, experience, education — `types.ts`'s `ResumeContent` extends `StaticResumeContent` with these) are no longer here: they're DB-backed and Admin-editable (see `CONTEXT.md`'s Resume Profile definition and [ADR 0015](./docs/adr/0015-resume-profile-becomes-db-backed-and-editable.md)), fetched at request time via `src/content/resumeProfileApi.ts`. Editing this file is still a code change for the UI-copy fields; editing the resume facts is now a Settings-page action, not a code change.
- `src/content/resumeProfileApi.ts` — `fetchResumeProfile()`, a `fetch` to `${NEXT_PUBLIC_API_URL}/resume-profile` tagged `next: { tags: ['resume-profile'] }` (Next's Data Cache: cached indefinitely until that tag is revalidated). Falls back to `@portifolio/shared`'s static `resumeProfile` default on any failure instead of throwing — `next build` prerenders `/` and the Blog layout against whichever API is live at build time, which on the very first deploy of the `/resume-profile` route is still the *previous* deployed API (both images build before either is swapped in, see `deploy.yml`) and would 404; crashing the build over that would be worse than briefly showing seed content until the Admin's next Settings save revalidates it.
- `src/i18n/index.ts` — locale registry. `useResumeContent(locale)` returns just the static per-locale UI copy (`StaticResumeContent`); `getResumeContent(locale)` is async and merges that with the live Resume Profile (`resumeProfileApi.ts`) into the full `ResumeContent` — use this one for anything that needs the resume facts (`src/app/page.tsx`, `src/app/blog/layout.tsx`). Only `en` exists today; adding a language means adding `src/content/<locale>.ts` (matching `StaticResumeContent`) and registering it here — no i18n library is used, by design.
- `src/app/api/revalidate-resume/route.ts` — a Route Handler, `POST`-only, called by the Settings page's Resume Profile editor right after a successful save: `revalidateTag('resume-profile', { expire: 0 })` busts the Data Cache tag above so the very next request re-fetches instead of serving one more stale copy (`{ expire: 0 }` rather than the usually-recommended `'max'` stale-while-revalidate profile, since this fires rarely, right after a deliberate admin edit, where correctness beats the perf win `'max'` is for). No auth guard — it only busts a cache tag, nothing sensitive to protect.
- `src/components/` — all plain Server Components (no `'use client'`, no framer-motion):
  - `SiteHeader.tsx` — not sticky, no section links: a mono wordmark, a one-line role/location note, and outlined `Blog` / `Resume ↓` controls, closed by a full-strength rule. Shared by the resume page and `blog/layout.tsx`; `section="blog"` inverts the Blog control, and `homeOrigin` prefixes the wordmark's `/#top` link when rendered under `blog.alisonrafael.me` (where a bare `/#top` would resolve on the blog's own origin). `Footer.tsx` is the matching mono footer with a "Back to top ↑" link.
  - `Hero.tsx` — two columns: oversized first/last name + serif statement on the left, a full-bleed grayscale portrait (`public/avatar.png`) with a black caption bar on the right.
  - `Section.tsx` — exports `Section` (index rail + serif headline + body; `flush` lets a full-bleed row list sit against the section's bottom rule), `Entry` (a mono-labelled block; wrap a run in `divide-y divide-line`), and `copyClass`.
  - `About.tsx` — the "years of experience / companies / roles held / certifications" numbers. All are derived at render time from the Resume Profile (date parsing + array lengths), never hand-entered — keep it that way so they can't drift out of sync.
  - `Experience.tsx` — a full-bleed list of rows (period + title/company + description), one per role, flattened across companies, newest first; the first role overall is labelled "Current role". Positional, not content-driven — reordering the profile's `experience` array changes which role is current.
  - `Skills.tsx`, `Credentials.tsx`, `Contact.tsx` — typographic lists and `Entry` blocks (no cards/pills); Contact puts the primary email in an outlined panel and the other links as labelled entries.
  - `src/lib/motion.ts` — the eased-transition constant, still used by the Admin Panel.
- `src/app/blog/` — the public Blog reading UI route files: `page.tsx` (`/blog` — a full-bleed list of rows, each a link with mono date/stats, serif title, excerpt and an arrow, inverting to black on hover) and `[slug]/page.tsx` (`/blog/:slug` detail — laid out like the home page: a two-column hero with the title/excerpt on the left and the cover image as a grayscale figure with a caption bar on the right, collapsing to one column when a Post has no cover, then `01 / Article` and `02 / Discussion` sections) are Server Components that call `src/blog/api.ts` directly with `{ cache: 'no-store' }` (a low-traffic personal blog where a just-approved comment or an incremented view count should show on next load, not wait out a revalidation window) — no `useEffect`/loading dance. `[slug]/page.tsx` also exports `generateMetadata`, producing real per-post `title`/`description`/`openGraph`/`twitter`/canonical tags server-side — a crawler reads this straight out of the rendered response, no client JS involved; this is what replaced the abandoned ADR 0011/0012 meta-injection approach. `react-markdown` + the markdown-rendering helpers run only here, server-side, so it's simply never in the client bundle for `/` or `/admin/*` (no manual lazy-load trick needed anymore, unlike the old SPA). `src/blog/api.ts` is deliberately separate from `src/admin/api.ts` — no coupling between the public site and the Admin Panel. The list payload carries `viewCount` and an approved `commentCount` per Post so the rows render without follow-up requests.
- `src/blog/components/` — the Blog's client islands, rendered as children of the server-rendered detail page: `ViewRegistrar.tsx` fires `POST /posts/:slug/views` once per real page view (a per-slug `useRef` guard stops React StrictMode's dev double-invoke from double-counting; see [ADR 0010](./docs/adr/0010-view-counter-intentionally-undeduplicated.md)) — this has to stay a genuine client component since a Server Component render isn't a real page view. `Comments.tsx` takes `initialComments` as a prop from the server parent (comment *content* is present in the initial HTML) but still submits new comments client-side, including 429-handling per [ADR 0009](./docs/adr/0009-reader-comments-pre-moderated-pseudonymous-one-level-rate-limited.md); it copies `formatRelativeTime` from `admin/pages/TrendsPage.tsx` rather than adding a relative-time dependency. `ShareButtons.tsx` receives `slug`/`title` as props. `MarkdownImage.tsx` is the `react-markdown` image-renderer used server-side.
- `src/app/admin/` — thin route files only (layouts + one-line re-exports like `export { PostListPage as default } from '../../../../admin/pages/PostListPage'`); all real Admin Panel logic still lives in `src/admin/` (see below), just re-routed to App Router conventions. `/admin/*` stays entirely client-rendered — [ADR 0006](./docs/adr/0006-admin-session-model.md)'s `localStorage`/JWT model means the server has no way to see the Admin's token, so none of this is server-side data fetching. `src/app/admin/layout.tsx` holds `AuthProvider` (wraps both `/admin/login` and the protected tree — both need `useAuth()`); `src/app/admin/(protected)/layout.tsx` (a route group — the parens don't affect the URL) holds `Gate` (the direct translation of the old `ProtectedRoute.tsx`: render `null` while `loading || !token`, `useRouter().replace('/admin/login')` in an effect otherwise — App Router's Client Components have no `<Navigate>`-during-render equivalent) plus `PendingCommentsProvider` and `AdminLayout` chrome.
- `src/admin/` — the Admin Panel's actual pages/components (see `CONTEXT.md` and [ADR 0005](./docs/adr/0005-admin-panel-in-web-client.md)). `AuthContext` holds the JWT in `localStorage` and calls `GET /auth/me` on mount to validate it, clearing it on failure — its `useState` initializer reads `localStorage` behind a `typeof window === 'undefined'` guard specifically because Next.js still server-renders this Client Component once for its initial HTML (see the note at the top of this section). `PendingCommentsContext` (mirrors `AuthContext`, rendered inside it) holds the count of `pending` Comments so `AdminLayout` can show a nav badge and `pages/CommentsPage.tsx` (the moderation UI — status filter, otherwise-hidden `authorEmail`, approve/reject/delete) can refresh it after each action without a navigation. `content/en.ts` + `i18n/index.ts` mirror the public site's `src/content`/`src/i18n` pattern — the Admin Panel is English-only by design, but its copy still lives in one typed file, not scattered JSX strings.
- `pages/PostEditorPage.tsx` — `@uiw/react-md-editor` is loaded via `next/dynamic(() => import('@uiw/react-md-editor'), { ssr: false })` since it touches browser APIs outside just render time (valid specifically because it's invoked from an already-`'use client'` file — inside a Server Component this pattern is disallowed); costs nothing behaviorally since this whole page is already client-only. `preview="live"` gives the split raw-markdown/rendered-preview view; its default toolbar "image" button is swapped via `commandsFilter` (not `extraCommands`) for one that opens a file picker and uploads through `POST /uploads`, and the same upload path is wired to the raw textarea's native `onPaste`/`onDrop` (via `textareaProps`) for drag/paste image insertion — both insert the returned URL at the cursor position. A separate "Cover image" picker (optional, above the editor) uploads through the same `POST /uploads` path and stores the returned URL as the Post's `coverImageUrl`. `data-color-mode="dark"` plus the `[data-color-mode='dark']` CSS variable overrides in `src/app/globals.css` repaint the editor's default GitHub-dark palette to match this site's theme tokens.
- `.env.production` / `.env.development` — `NEXT_PUBLIC_API_URL`, read by both `src/blog/api.ts` and `src/admin/api.ts`. Committed (not secret, just the API's public hostname) since Next.js bakes `NEXT_PUBLIC_*` vars in at build time; there's no runtime env injection for this deployment.
- `pages/TrendsPage.tsx` — the "Get top trends" flow (see `CONTEXT.md`'s Trend/Trend Search definitions and [ADR 0007](./docs/adr/0007-anthropic-api-for-trend-discovery.md)): on mount, `GET /trends/searches/latest` shows the last saved Trend Search — this never triggers a new Claude call. `POST /trends/discover` only runs when the Admin presses "New search"; multi-select checkboxes over the results, `POST /trends/drafts` for the selected ones. Per-item `created`/`failed` results render inline (best-effort batch, not all-or-nothing).
- `pages/SettingsPage.tsx` — below the password-change form, a Resume Profile card: fetches `GET /resume-profile` on mount and shows it pretty-printed in a plain monospace `<textarea>` (raw JSON, not a structured form — the Admin already hand-edits this exact shape in `shared/src/resume.ts`'s seed default today, so this isn't a new kind of editing burden). Saving `JSON.parse`s client-side first (inline error, no request sent, on invalid JSON), then `PATCH /resume-profile`, then fires `POST /api/revalidate-resume` (best-effort — a failure there just means the public page waits out its own cache lifetime instead of updating immediately, since the save itself already succeeded).
- `pages/ToolsAtsResumePage.tsx` — mirrors `ToolsCoverLetterPage.tsx`'s job-description `<textarea>` (same label/placeholder copy shape), but the result renders in `MDEditor` (same dynamic-import pattern as `PostEditorPage.tsx`) instead of a read-only textarea, since this content is meant to be edited before approving. On mount, restores both the last draft's markdown *and* its job description from `GET /ats-resume/latest`, so reopening the tool shows what the last draft was tailored for.
- `src/proxy.ts` — Next.js's App Router proxy (renamed from `middleware.ts` in Next.js 16; the exported function is named `proxy`, not `middleware`). Redirects `www.alisonrafael.me` → `alisonrafael.me` (308), reading the target protocol from `x-forwarded-proto` since nginx-proxy terminates TLS and forwards plain HTTP internally — this app owns its own canonicalization instead of an nginx-layer rule, since `generateMetadata`'s canonical/`og:url` need one stable host.
- `src/lib/resumeUrl.ts` — exports `resumeDownloadUrl` (`${NEXT_PUBLIC_API_URL}/resume`), the public "Download Resume" URL used by `SiteHeader.tsx`'s `Resume ↓` control. There is no static `public/resume.pdf` anymore — the file is generated and approved via the ATS Resume Generator Tool and served by `server` (see `server/src/ats-resume/` and [ADR 0014](./docs/adr/0014-ats-resume-generator-replaces-static-download.md)); it can't be a `web-client` static asset since `public/` is baked into that Docker image at build time and can't be updated at runtime.

### `server/`

- `src/health/` — `GET /health` for container/deploy healthchecks.
- `src/auth/` — the single Admin account. `AuthService` seeds it from `ADMIN_EMAIL`/`ADMIN_PASSWORD` on first boot only (`OnModuleInit`, skipped if an Admin already exists — those env vars aren't re-applied after that). `POST /auth/login` returns a JWT (`JWT_EXPIRES_IN_SECONDS`, a number of seconds — not a duration string; `@nestjs/jwt`'s `expiresIn` treats a numeric *string* as milliseconds but a numeric *type* as seconds, so this must stay `Number(...)`-converted). `GET /auth/me` and `PATCH /auth/me` (both `JwtAuthGuard`) are self-service only — the authenticated Admin viewing/changing their own password (current-password re-entry required; see `CONTEXT.md`'s Admin definition and [ADR 0006](./docs/adr/0006-admin-session-model.md)) — there's no route to manage any *other* account, by design. `AuthModule` exports `PassportModule` (pre-`.register()`'d with the `'jwt'` strategy) so other modules get `JwtAuthGuard` support by importing `AuthModule` — don't re-register `PassportModule` elsewhere, it won't provide the DI token other modules need.
- `src/blog/` — the Blog. `BlogController` deliberately declares the admin routes (`/posts/admin`, `/posts/admin/:id`, all `@UseGuards(JwtAuthGuard)`) before the public routes (`/posts`, `/posts/:slug`, `POST /posts/:slug/views`) — keep that order, Nest matches routes top-down. `BlogService.update()` sets `publishedAt` when `published` flips to `true` and clears it back to `null` when it flips to `false` (see the Post/Admin definitions in `CONTEXT.md`). The `Post` entity has an optional `coverImageUrl` and a `viewCount` (default 0). `findPublished()` is a QueryBuilder that maps an approved-only `commentCount` onto each Post via `loadRelationCountAndMap`; `registerView()` is an atomic `increment` (see [ADR 0010](./docs/adr/0010-view-counter-intentionally-undeduplicated.md)).
- `src/comments/` — reader Comments on Posts (see `CONTEXT.md` and [ADR 0009](./docs/adr/0009-reader-comments-pre-moderated-pseudonymous-one-level-rate-limited.md)). `CommentsController` is also `@Controller('posts')` (so the public URLs are `/posts/:slug/comments`), admin/literal routes declared before the `:slug`-bearing ones. Public: `GET /posts/:slug/comments` (approved only, one level of replies, `authorEmail` never returned) and `POST /posts/:slug/comments` (creates a `pending` Comment; the only route guarded by `CommentRateLimitGuard`, a small in-process fixed-window limiter — 5/IP/hour, no dependency; see ADR 0009 for why not `@nestjs/throttler`). Admin (`JwtAuthGuard`): `GET /posts/comments/admin[?status=]`, `GET /posts/comments/admin/pending-count`, `PATCH /posts/comments/admin/:id/status`, `DELETE /posts/comments/admin/:id`. `Comment` is the schema's first relational entity — `@ManyToOne` to `Post` and a self-referencing `parent`, both `onDelete: 'CASCADE'`; `authorEmail` is `select: false` so public queries can't leak it. One-level threading is enforced server-side (a reply whose parent already has a parent, or whose parent is on another Post, is rejected).
- `src/uploads/` — Upload images embedded in Post markdown (see `CONTEXT.md`). `POST /uploads` (`JwtAuthGuard`, multer `diskStorage`, images only, 5MB cap) saves into `UPLOADS_DIR` (env-overridable, defaults to `./uploads` relative to `process.cwd()` — that's `/app/uploads` under `server/Dockerfile`'s `WORKDIR`, where `docker-compose.yml` mounts a persistent volume; see [ADR 0004](./docs/adr/0004-local-disk-image-storage.md)) and returns an absolute URL built from the request's own host/protocol — no hardcoded public-URL env var needed. `ServeStaticModule` in `app.module.ts` serves that same directory back out at `/uploads/*`. `main.ts` sets `trust proxy` so `req.protocol` reports `https` correctly behind nginx-proxy; without it, uploaded image URLs would come back as `http://`.
- No admin UI in the API itself — `web-client/src/admin/` (above) is the Admin Panel; `server/` stays UI-agnostic, just JSON + file responses.
- `src/trends/` — the three chained Claude calls behind "Get top trends" (see [ADR 0007](./docs/adr/0007-anthropic-api-for-trend-discovery.md)): `TrendsService.discover()` runs the web-search-backed discovery agent (topic + one-line summary only, deliberately light — see ADR 0007's update) then the Tech-Stack relevance filter, and saves the ranked result as a new `TrendSearch` row (`POST /trends/discover`) — `getLatestSearch()` (`GET /trends/searches/latest`) reads the newest row back with no Claude call at all, which is what `TrendsPage.tsx` calls on mount instead of auto-discovering (see ADR 0007's persistence addendum). `createDrafts()` runs the draft-writer agent once per selected Trend — this is the step with its own `web_search` tool and the only place a full write-up gets generated, bounded by the Admin's selection rather than discovery breadth — and saves each via the existing `BlogService.create()`, best-effort, retrying a slug collision with a numeric suffix rather than failing that item (`POST /trends/drafts`). All three routes are `JwtAuthGuard`-protected like the rest of the admin API; the two `POST`s wrap the service call in a try/catch that rethrows as `BadGatewayException` with Claude's real error message — deliberately not Nest's default opaque 500, since this is a single-admin tool with no one else to hide internals from. Every Claude call's `system` prompt demands a bare JSON response (no prose, no code fences); `extractJson()` in `trends.service.ts` parses that (checking `stop_reason` to give an actionable error if the response was truncated), with a fallback that slices out the first-to-last bracket/brace if the model wraps it in anything else.
- `src/resume-profile/` — the Resume Profile, DB-backed (see `CONTEXT.md`'s Resume Profile definition and [ADR 0015](./docs/adr/0015-resume-profile-becomes-db-backed-and-editable.md)). `ResumeProfileEntity` is a JSON-blob singleton row (`@Column({ type: 'json' }) data: ResumeProfile`, same idiom as `TrendSearch`'s `trends` column), seeded once from `@portifolio/shared`'s static `resumeProfile` default (`OnModuleInit`, mirrors `AuthService`'s admin seed). `GET /resume-profile` is public (the site itself reads it unauthenticated); `PATCH /resume-profile` (`JwtAuthGuard`, `UpdateResumeProfileDto` — a full nested DTO tree mirroring every `ResumeProfile` shape, required for `main.ts`'s global `whitelist`/`forbidNonWhitelisted` `ValidationPipe` to validate correctly through nested arrays) is a full replace, not a patch. `ResumeProfileModule` exports `ResumeProfileService` for `ToolsModule` and `AtsResumeModule` to inject — both fetch `await this.resumeProfile.get()` at call time now instead of importing the static `resumeProfile`, so an Admin edit reaches every Claude-facing tool immediately.
- `src/ats-resume/` — the ATS Resume Generator Tool and the public resume download, replacing the old static `web-client/public/resume.pdf` (see `CONTEXT.md`'s ATS Resume Generator definition and [ADR 0014](./docs/adr/0014-ats-resume-generator-replaces-static-download.md)). `AtsResumeService.generate(jobDescription)` (`POST /ats-resume/generate`, `JwtAuthGuard`) fetches the live Resume Profile, makes one Claude call grounded in it (reusing `formatResumeProfile()`/`extractText()`, exported from `tools/tools.service.ts` rather than duplicated) with a system prompt that explicitly permits emphasizing/reordering/rephrasing toward the given job description but forbids adding any employer, title, skill, achievement, or date not already in the profile, and saves a new `AtsResume` row (`markdown` + the `jobDescription` it was tailored to); `getLatest()` (`GET /ats-resume/latest`) reads the newest row back with no Claude call, same "show last draft for free" pattern as Trends — including the job description, so reopening the tool shows what the last draft was tailored for. `approve()` (`POST /ats-resume/:id/approve`) takes the Admin's final (possibly hand-edited) markdown, renders it to PDF via `render-resume-pdf.ts` (a small hand-rolled `pdfkit` renderer — not a general markdown-to-PDF library, since the system prompt already constrains Claude to only the constructs an ATS parser cares about: headings, bullets, plain paragraphs), and overwrites a fixed `resume.pdf` on the persistent Uploads volume (`RESUME_PDF_PATH`, `join(UPLOADS_DIR, 'resume.pdf')`) — always the same filename, so the public URL never changes. `ResumeController` (`@Controller('resume')`, **no guard**) serves that file at `GET /resume` with a friendly `Content-Disposition` filename; this is what the public site's download links point at. `AtsResumeService.onModuleInit()` seeds `resume.pdf` from a bundled `server/assets/resume-seed.pdf` on first boot if nothing's been approved yet (mirrors `AuthService`'s admin-seed pattern), so the download link is never broken pre-launch.

## Deployment

Single DigitalOcean droplet (Ubuntu 22.04, domain `alisonrafael.me` already pointed at it), Dockerized. Three services now run behind the shared reverse proxy:

- `web-client/Dockerfile` — multi-stage: builds the Next.js app with Node (`output: 'standalone'`, see [ADR 0013](./docs/adr/0013-migrate-web-client-to-nextjs-app-router.md)), then runs it with `node web-client/server.js` in a second Node stage — no nginx container anymore. The standalone build doesn't copy `.next/static` or `public/` into its own output tree (a documented Next.js gotcha), so the run stage's `COPY`s add both by hand alongside the traced `node_modules`/`server.js`. `docker-compose.yml`'s `web` service sets `VIRTUAL_PORT: 3000` explicitly since nginx-proxy can no longer auto-detect the port from a single-`EXPOSE` nginx base image. Publicly reachable at `alisonrafael.me` / `www.alisonrafael.me` (`src/proxy.ts` 308-redirects the `www` host to the apex one). Build context is the **repo root** (`docker build -f web-client/Dockerfile .`), not `web-client/` — it depends on the `shared/` workspace, which cost it the self-contained build it used to have (see [ADR 0008](./docs/adr/0008-shared-workspace-for-cross-app-data.md)); the build stage runs `npm run build --workspace=shared` before `--workspace=web-client`.
- `server/Dockerfile` — multi-stage: builds the NestJS app with Node, runs the compiled `dist/main.js`. Build context is the **repo root**, not `server/` (`docker build -f server/Dockerfile .`), because npm workspaces hoist the lockfile and `node_modules` there — and now also because it needs `shared/dist` built and copied into both the build and runtime stages. Also copies `server/assets` (the ATS Resume Generator's boot-time seed PDF, see `src/ats-resume/` above) to `./assets` in the runtime stage, matching `UPLOADS_DIR`'s cwd-relative convention. Publicly reachable at `api.alisonrafael.me`.
- `mariadb` (root `docker-compose.yml`) — not on the `nginx-proxy` network, only on the `internal` one shared with `api`; never publicly reachable.
- `docker-compose.yml` (root) — all three services. `web` and `api` join the external `nginx-proxy` network and set `VIRTUAL_HOST`/`LETSENCRYPT_HOST` for cert/routing auto-discovery; `api` and `mariadb` also share an `internal` network for DB traffic. Reads deploy-time secrets (DB credentials, JWT secret, admin seed) from a `.env` file next to `docker-compose.yml` on the droplet — see root `.env.example` for the shape (distinct from `server/.env.example`, which is for running the API locally without Docker). That `.env` is never hand-edited on the droplet: see below, `deploy.yml` regenerates it from GitHub Actions secrets on every deploy.
- `deploy/proxy/` — the shared `nginx-proxy` + `acme-companion` reverse-proxy stack, deployed **once** on the droplet, independent of any single app's lifecycle. See `deploy/proxy/README.md` and [ADR 0001](./docs/adr/0001-nginx-proxy-acme-companion-for-tls.md) for why this shape was chosen over hand-rolled nginx+certbot or a single-container Caddy setup. `vhost.d/api.alisonrafael.me` bumps `proxy_*_timeout` to 180s there specifically, since the trend-discovery/draft-creation endpoints (chained Claude calls with web search) can run well past nginx-proxy's 60s default — this stack's own README explains why a normal `deploy.yml` push never picks this up automatically.
- `.github/workflows/deploy.yml` — on push to `main`: builds and pushes both images to GHCR, then scp's `docker-compose.yml` to the droplet (the repo itself isn't cloned there, so this is the only way that file stays current), SSHes in to write `.env` from GitHub Actions repo secrets, and runs `docker compose pull && up -d`. Needs these repo secrets configured (Settings → Secrets and variables → Actions) before it can run: `DROPLET_HOST`, `DROPLET_USER`, `DROPLET_SSH_KEY`, `DROPLET_APP_DIR` (existing, from the v1 deploy) plus `DB_ROOT_PASSWORD`, `DB_PASSWORD`, `JWT_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ANTHROPIC_API_KEY`.
- The comment rate limit (`CommentRateLimitGuard`, see [ADR 0009](./docs/adr/0009-reader-comments-pre-moderated-pseudonymous-one-level-rate-limited.md)) is a hardcoded constant in `server/src/comments/` — no new dependency, env var, secret, `docker-compose.yml`, or `deploy.yml` change. If it's ever made configurable, that's when the `.env.example` × 2 / `docker-compose.yml` `api` env block / `deploy.yml` `.env` heredoc / GitHub secret chain all need updating together.
